## 原则

- 清晰优先：命名、结构和控制流应直接表达业务或技术意图，优先让维护者读懂。
- 高内聚低耦合：相关数据和行为放在清晰边界内，跨模块依赖保持少且方向稳定。
- 单一职责：类、函数和模块应有主要职责，避免万能 Service、Manager、Helper 或 Utils。
- 简单设计：优先使用满足当前需求的最简单方案，只有复杂度明显下降或本地模式已经存在时才增加抽象。
- DRY 但不过度抽象：消除真实重复，语义不同的相似代码不要强行合并。
- SOLID 重在判断：用原则识别职责混乱、扩展困难、依赖方向错误和接口臃肿，不为形式制造过度分层。
- 可测试性：核心逻辑尽量可独立验证，IO、数据库、网络、时间和随机数等副作用与业务判断隔离。
- 显式依赖：重要依赖、配置、边界条件、默认值、跨层调用和外部系统依赖应能从代码或配置追溯。
- 错误处理清晰：不吞异常，不用空返回、默认值或宽泛 catch 掩盖失败，错误信息应帮助定位问题。
- 安全默认：权限、认证、会话、输入校验、SQL、上传、反序列化和敏感数据默认按高风险处理。
- 演进式重构：重构应小步、可回滚、可验证，并围绕当前目标或明确风险，不做无关大改。
- 保持局部一致性：新代码优先匹配当前模块的命名、分层、错误处理和测试习惯。
- 交付与可运维性：构建、测试、部署、配置和运行入口应清晰、可重复、可追溯。
- API 与数据兼容性：已有 API 路径、方法、字段、响应、分页和错误语义默认保持兼容；数据库、字典、状态枚举和迁移脚本按高风险处理。
- 依赖与供应链治理：新增依赖前确认现有依赖无法满足需求；依赖升级要考虑传递依赖、兼容、安全、构建影响和回滚。
- 性能与容量意识：分页、批量导入导出、递归查询、定时任务、缓存和文件处理默认按性能敏感路径处理。
- 可观测性与故障诊断：关键业务动作、外部依赖、异步任务和失败路径应保留足够诊断信息。
- 文档与知识沉淀：稳定的架构事实、模块边界、运行入口、质量检查和风险约束应沉淀到项目文档或 Harness。
